# 相对评分标准（评审工作口径草案）

更新：2026-10-29。本文是当前评审团队用于**相对判断与人工复核**的工作口径，
不是 OB 官方已冻结的评分规则，也不替代平台 `resultType=1` 的二值回传协议。
平台当前是单子题固定分：通过按任务 `maxScore` 计分（当前为20），不通过为0。

## 1. 核心原则

1. **实际行为优先于自述和文档**：README、截图、日志只能作为线索；关键结论应由固定提交的代码、
   可复现测试、真实后端交互或可核对的原始记录支持。
2. **MiniMax 是否参与不是独立一票否决项**：有真实开发记录是加强可信度的证据，但没有该记录不自动判0。
   评审重点是最终交付是否完成题目要求、是否能复现和是否诚实披露来源。
3. **环境阻塞不等于选手功能失败**：缺少裁判侧 PowerContext、Docker、网络或依赖时，标记
   `blocked`/`not_run`，不要直接变成 `fail`。但提交自身缺失必要依赖、说明无法完成干净启动，
   可以作为可运行性缺陷。
4. **报告有效不等于作品通过**：Harbor `report_valid=1` 只表示报告结构和证据哈希有效；不能映射成20分。
5. **证据分层**：每个结论标记 `rerun`（本次独立复跑）、`supplied_record`（选手/操作员提供的记录）、
   `static`（代码/文件静态事实）或 `not_run`。不要把不同层级混写成“已验证”。
6. **只评固定版本和规定目录**：平台分支/完整 commit 是唯一对象；五家共用仓库只看 `minimax/`。
   不用当前分支 HEAD 替换平台指定 commit，不把工作树临时修改算进成绩。

## 2. 六个评审维度

六维度用于结构化复核和发现风险，**当前不要求六项每一项都有选手提交日志**。

### A. 可运行性（runtime）

检查：

- 依赖、入口、配置和数据初始化是否写清楚；
- 能否在清洁、受控环境启动，不依赖未交付的本地文件、宿主服务或私密状态；
- 任务样例、目标测试和回归测试是否能按说明运行；
- 依赖外部服务时，服务版本、启动方式、端口、网络和重置方法是否明确。

建议判断：

- **强通过证据**：固定环境独立启动、命令退出成功、清洁状态可重置；
- **部分/复核**：代码完整但裁判环境缺服务或只完成静态核对；
- **不通过风险**：交付目录必需文件缺失、说明与实际入口冲突、只能依赖提交外的个人环境。

### B. 上下文正确性（context）

检查：

- 规格、代码、测试之间是否有可追溯来源；
- 任务上下文是否选择当前相关约束，而非只做全文摘要；
- 规格更新并重新导入后，后续上下文是否使用新版本、没有继续使用过期内容；
- 引用路径、行号、digest/excerpt 是否能回到固定提交核对。

**强证据**：重导入前后同一任务的上下文对照，更新后的 digest/excerpt 和来源核对均通过。

### C. 真实数据库参与（database）

检查：

- seekdb/OceanBase 是否实际保存规格、代码、测试等资料；
- 是否真实执行查询/检索，查询结果是否进入最终上下文；
- 是否存在 memory fallback 冒充数据库成功的情况；
- SQL、集合、索引或后端调用记录是否能与代码和结果对应。

**强证据**：真实后端初始化/入库统计、查询通道结果、上下文 citations 共同成立。
单纯依赖声明、README 提及、mock/fake 或 `--index memory` 不足以证明真实数据库参与。

### D. 状态复用（state）

检查：

- 任务状态是否真实写入 PowerContext，而不是只写本地 JSON；
- 进程A保存后退出，进程B新启动能否读取同一状态；
- 读取的状态是否实际进入后续上下文或任务流程；
- scope、task_id、版本和状态内容是否一致，是否有污染其他任务的风险。

**强证据**：独立进程 `record` → 进程结束 → 新进程 `status/resume`，返回 `found=true` 或等价结果，
并且上下文使用读取出的状态。仅有 API 客户端代码或单进程 read-back 是较弱证据。

### E. 有效代码修改（code_change）

检查：

- 任务目标行为是否真的实现；
- 同一组目标测试在基线失败、修改后通过；
- 原有回归测试通过；
- 测试预期和断言没有被删除、弱化或跳过；
- before/after 测试文件、基线 commit 和 diff 能对应；
- 修改没有超出任务范围破坏既有行为。

**强证据**：固定基线上的目标 FAIL → 固定提交目标 PASS，回归 PASS，测试文件字节一致或有明确合理修改。
只看 after 快照、只看自述日志、或只看编译成功不够。

### F. 开发工具/模型记录（minimax）

这是**可信度与可审计性维度，不是独立硬门槛**。检查：

- 若选手声称使用 MiniMax，是否有任务、上下文、请求/响应摘要、用量、diff 和测试结果的对应记录；
- 记录是否在固定提交中，是否与实际改动文件和时间线一致；
- 是否把评审方后来调用的 MiniMax 误当成选手参与证据；
- 缺少记录时，明确写“未证实”，不要自动推定造假或自动判0。

选手最终代码和行为已经满足核心要求时，缺少模型记录通常应作为**证据完整性/复核风险**，
而不是单独否决；除非正式题面明确把该记录列为硬性资格条件，且该口径已对所有选手统一发布。

## 3. 相对结论分级

这不是平台分值，而是帮助评委在二值回传前对齐判断：

| 结论 | 使用条件 | 平台动作建议 |
| --- | --- | --- |
| **通过候选（strong pass）** | 核心运行、上下文、数据库、状态、代码修改均有独立或可核对强证据；无关键诚信/范围问题 | 用户确认后可考虑 `pass` |
| **通过候选（evidence-light）** | 核心行为已实际通过，但部分高级证据来自静态/选手记录；缺失项不影响题目已明确的核心验收 | 先人工复核；理由中写清证据等级 |
| **需人工复核（review）** | 关键维度被环境阻塞、证据互相冲突、报告有效但实质行为未完全复现，或评分口径存在歧义 | 不自动回传；补跑/询问出题方 |
| **不通过候选（fail）** | 固定提交实际违反已发布核心要求：目标行为失败、回归被破坏、数据库/状态声明与真实行为冲突、缺少核心交付物等 | 用户确认后回传 `fail` |
| **执行错误（error）** | 评测方无法取得固定版本、临时认证/网络/裁判基础设施导致无法完成评测，且未核实为下述仓库不可访问情况 | 按实际协议回传 `error`/对应 failMsg |

### 已核实仓库不可访问：直接0分

用户与 PsiACE 确认的新口径：提交仓库经核实确实无法访问，直接判0分。
这不是代码测试失败，也不需要虚构检出或启动 Harbor。仅一次 `Repository not found`、
缺 PAT、TLS错误或网络超时不能自动视为核实；需保留核实来源和拉取失败记录。

回传采用 `fail`（`taskStatus=2`，子题不通过/0分），不是 `error`（`taskStatus=3`）。
使用 `review.py submit --verdict fail --confirmed-repo-unavailable --reason '核实依据…'`，
仅允许 `fetch_failed` 且 `fetch_fail_msg=4`、平台指定分支/commit与本地记录一致的任务。
版本是平台指定版本，**不声称已检出验证**；租约和ACK检查仍保留。该开关目前只在 Python CLI 提供。

## 4. 已完成作品的应用示例（task 47213508）

本节是本次案例的**分析结果，不是普遍预设**：

- `code_change`：通过候选。before 目标8失败/回归9通过，after17通过，测试文件未改弱；
- `database`：通过候选。真实嵌入式 seekdb 入库49条并参与上下文检索；
- `context`：通过候选。40候选、7规格、4代码、8测试，规格重导入后 digest/excerpt 变化；
- `state`：通过候选。固定提交同伴随 PowerContext 服务，进程A `record`、进程B `status found=true`；
- `runtime`：部分/复核。核心模块可运行，但完整交付目录依赖仓库根 PowerContext，完整demo不是一次性清洁运行；
- `minimax`：未证实。提交缺少选手开发记录，但按本口径不作为单独否决理由。

综合建议：**通过候选，保留运行边界和证据缺口说明**。这是评委建议，不能绕过用户对平台不可逆回传的确认。

## 5. 必须明确的边界

- 过期任务回传需要平台方允许；`--allow-expired` 只绕过本地安全护栏，不保证平台接受，仓库不可访问例外也不绕过此检查。
- `recover`仅用于fetch_failed、有固定commit、现存匹配凭据且租约有效的任务；不支持过期覆盖，不重新领取/续租。成功后进入awaiting_review按常规复核。
- 网络不确定的回传需冻结请求、核对 ACK；本地人工路径仍在补 outbox 能力。
- Harbor Agent 允许联网不代表能接触宿主凭据、Docker socket 或其他任务；模型 key 用短期、限额凭据。
- 任何“全部通过”都必须带命令、固定 commit、环境、时间和证据路径；没有证据就写 `not_run`/`blocked`。
