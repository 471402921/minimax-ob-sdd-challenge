## 环境与耗时（2026-10-29 实测）

- 真实任务 `47214128` 前一轮的耗时构成：工具执行约20分25秒，模型响应/调度间隙约6分24秒；
  其中5次 `bootstrap.sh` 合计约12分42秒，样例回放本身仅约36秒。
- 根因：只预热了服务端 venv（旧镜像 PowerContext 1.2.0）及少量 seekdb wheel，选手自己声明的
  `powercontext[cli,server,seekdb]==1.4.0` 完整依赖仍需联网下载。服务端与客户端版本也因此不一致。
- 修正：`prewarm_wheels.py` 用同一份已解析 wheel 集同时生成服务端 venv 和选手离线缓存。
  断网验证：选手 `bootstrap.sh` 26秒完成；服务端 1.4.0 就绪；选手自启服务后完整样例回放
  （含8/8重启复用状态）约95秒。热路径合计约2分11秒。
- 该提交自带的 `scripts/start_powercontext.sh` 使用 `ACCESS_MODE=disabled`、端口8000、
  seekdb后端；评审侧强推的18000+bearer服务与其不一致，是此前401/422的可能原因。
  现要求优先使用选手自身文档的服务方式，评测侧服务仅作外部依赖兜底。
- 1 GiB/2 GiB/4 GiB 对照：1 GiB 能完成但 `memory.events max` 触顶3804次；2 GiB 零触顶零OOM且耗时相同。
  现所有 profile（含 backend）默认 2 GiB，重任务用 `--memory-mb 4096`；1 GiB 不作为默认。
  对照未含 Pi 模型进程，首批仍需采样实际峰值。上一轮在旧镜像下超过 30 分钟 Agent 上限，
  新镜像尚未完成完整模型轮次验证。
- 上述2分11秒与 16.3 分钟的批次都不含人工复核，所以**10分钟是热路径目标，不是对所有新提交的保证**；
  冷依赖、复杂后端和疑难排查必须走单独的环境准备/人工分流。
- 4 路批次的时间构成（约 10 分钟时采样）：工具 43.5%、模型回合 56.5%，199 回合、
  平均每回合 11.8 秒、缓存命中 95.9%。两条任务各有一条 **240.1 秒**的安装命令白烧。
  据此做了两项低风险优化（不改变模型判断）：审计通过时 `PIP_NO_INDEX=1` 让联网尝试秒失败；
  `prepare_venv.py` 只建一次 venv（requirements 哈希戳记）供所有 scratch 目录复用。
  这两项尚未在新批次上实测收益。
- 安装预算改为可配置，默认 install 240s、tests/backend 120s（`runtime_guard.py start --install-seconds N`），
  仍按阶段累计。单任务那次真实提交首次 `bootstrap.sh` 在 81.8 秒被旧120秒预算截停，说明默认值需要放宽。
- 依赖审计现在支持：extras、范围版本、`sys_platform` 等可判定标记，以及无 tomllib 时的受限
  `[project].dependencies` 回退解析；无法判定的标记仍保持阻塞，不做猜测。

## 恢复与特殊判定

- 任务仓库凭据在clone前存仓库外私密目录，绑定任务/版本/租约。recover不重新领取、不续租。
- 原先丢失凭据的任务后来获得替换授权并完成，**不再处于等待恢复状态**。
- 默认拒绝过期回传；--allow-expired仅在平台/用户明确允许后使用，不能作为生产调度策略。
- 用户与PsiACE确认：仓库经核实不可访问可按fail/0分回传；单次缺PAT/网络报错不自动成立。
  Python CLI的--confirmed-repo-unavailable保留租约、版本与ACK检查，不虚构检出。
- MiniMax开发记录不是独立一票否决项，缺记录如实标未证实。
