# 批量评测运行器（首版，非自动评分）

## 环境准备（推荐：wheels 镜像）

**先解决“版本匹配 + 依赖缓存”，再谈超时。** 早期只预热了服务端 venv，选手自己的
`pip install` 仍是冷下载，单次真实任务里 5 次 bootstrap 共耗约 12 分钟。

`harbor/prewarm_wheels.py` 用一个**已解析的离线 wheel 集**同时生成：

1. `/opt/pc-venv`：trial 本地 PowerContext 服务；
2. `/opt/wheels/player`：选手 `.venv` 的离线缓存（镜像内 `PIP_FIND_LINKS`）。

因此服务端与客户端版本不会因镜像而偏离。实测（Python 3.11 / cp311 wheel）：

```text
构造 wheel 集（宿主，一次性）: pip wheel -r requirements.txt  → 128 wheels / 125 MiB
镜像内选手 bootstrap（断网）  : 26 秒（此前 5 次 ×180 秒超时）
```

```bash
python3 harbor/prewarm_wheels.py --prepare --wheels workdir/wheelhouse-pc140
sudo -n python3 harbor/prewarm_wheels.py --build          # 需要 Docker 权限
sudo -n python3 harbor/prewarm_wheels.py --verify \
  --requirements workdir/task-<id>/minimax/requirements.txt   # 断网安装 + pip check
```

`--verify` 只有在**全部依赖都能从镜像内 wheel 集离线安装**时才退0；它不声称是官方包的
唯一合法来源，也不证明未被缓存的其它依赖能安装。构建会核对逐文件 hash（`inputs.json`），
拒绝软链/非 wheel 文件，并要求 wheel 集里确有 `powercontext 1.4.0`。

`harbor/prewarm.py`（旧路径）仍可用：它从固定 Git 对象导出 PowerContext 源码并装成
1.2.0。**该版本与 1.4.0 客户端不匹配，只保留作历史/对照；新任务用 `prewarm_wheels.py`。**

`prepare.py` 会记录本地不可变镜像 ID（`--base-image sha256:...`），BuildKit 不能直接用
裸 sha256 作 `FROM`，因此仓库用内容命名本地 tag（`harbor/prewarm:sha-<id>`），
`batch.py` 启动前校验 tag 仍指向该 ID。

**不要把镜像 ID 手抄进命令**：长哈希抄错一个字符会让 batch 在启动阶段以
“prewarmed image tag is absent or changed” 拒绝，看起来像代码 bug。应始终程序取值：

```bash
REAL=$(sudo -n docker image inspect harbor/review-wheels:local --format '{{.Id}}')
sudo -n docker tag harbor/review-wheels:local "harbor/prewarm:sha-${REAL#sha256:}"
python3 harbor/prepare.py --task-id ID --repo workdir/task-ID --commit SHA --base-image "$REAL"
```

## 领取与暂存并行（`harbor/wave.py`，2026-10-30）

`judge/review.py fetch` 一次只领一条并顺带 clone 仓库；串行做 44 条会把租约耗在打包上
（此前 30 分钟窗口只剩 20 分钟执行，`47225900` 因此只写出基础设施检查点）。
`wave.py` 用一个领取线程 + 多个暂存线程重叠这两步：

```bash
source ~/.config/minimax-ob-judge/platform.env
python3 harbor/wave.py --base-image sha256:<id> --count 46 --workers 4 --tag 44e
ALLOW_UNCACHED=1 TRIALS=45 BACKENDS=2 TIMEOUT=1800 \
  MIN_DISK_GIB=100 bash harbor/start_service.sh workdir/manifest-44e.json batch44e-run
```

- 实测：17:28 开始领取，17:34:52 完成 46 条领取 + 45 条暂存（1 条提交无 `minimax/` 直接判 0）。
- 凭据扫描默认严格；失败才逐级放宽到 `--acknowledge-fixture-secrets` /
  `--acknowledge-secret-files`，放宽级别写入暂存 manifest 的 `credential_scan`。
- 租约检查在 `batch.py` 侧：要求 `timeout + 900s` 小于剩余租约，所以租约 53 分钟时
  最多只能用 30 分钟执行窗。领取前先看 `queue-count`，不要把 40 分钟窗口塞进 30 分钟租约。

## 两项低风险提速（2026-10-29 实测驱动）

1. **离线 pip 快速失败**：审计确认所有声明 pin 命中缓存时，`prepare.py --offline-install`
   会在镜像里写 `PIP_NO_INDEX=1 PIP_TIMEOUT=5 PIP_RETRIES=0`。此前有两条提交在依赖已缓存
   的情况下仍然联网，各自白烧满 240 秒预算；离线模式让这类尝试约 1 秒失败，审阅者据此改走
   缓存，而不是等待。
2. **一次建 venv、多份复用**：`reviewer-skill/prepare_venv.py` 在提交副本之外建
   `/work/review/venv`，用 requirements 哈希做戳记；重复调用直接 `reuse`。实测同一提交曾
   在 6–8 个 scratch 目录各装一遍（每次约 20 秒）。

```bash
python3 harbor/prepare.py --task-id ID --repo workdir/task-ID --commit SHA \
  --base-image "$REAL" --offline-install
python3 /opt/reviewer-skill/prepare_venv.py --requirements minimax/requirements.txt
python3 /opt/reviewer-skill/prepare_venv.py --requirements minimax/requirements.txt   # reuse
```

这两项都不改变审阅判断本身：模型仍要独立核对证据，只是不再重复消耗在可避免的下载上。

## 并发上限与租约预留（实测）

- 入场预算是 `可用内存 - 16 GiB`；light 每条预留 3 GiB、backend 4 GiB。
  35 GiB 可用时只放得下 **7 条 light**，即使 `--trials 8` 第 8 条也只会排队。
- 排队任务仍消耗租约。启动前检查 `timeout + 900s` 是否落在剩余租约内；
  6 路批次墙钟约 10 分钟，8 路批次约 28 分钟，排队越长越容易在轮到前失效。
- 容器实测峰值低于 1 GiB，但预留刻意保守；要真正跑到 8 路，应同时提高入场预算
  和领取租约（或缩短单条超时），不要在批次进行中偷偷下调预留。

## 依赖版本策略（重要边界）

当前 wheelhouse 是**一次性快照**（2026-10-29 由 task47214128 的 pin 解析得到，powercontext 1.4.0）。
后果分两类：

- **精确 pin**（如 `powercontext[builtin]==1.4.0`）——评测版本与提交声明一致，可信；
- **范围 pin**（如 `>=1.2.0`）——pip 今天会解析到 **1.4.1**，而评测用的是快照 1.4.0。
  必须在报告里披露，不能声称复现了“今天 pip 会装的那套”。

本轮已有实例：47216546 在 1.2.0 下全链路可用，但其范围会解析到 1.4.x，而 1.4.x 会拒绝其
`DirectCandidatePipeline`。这类差异应作为“版本约束过宽”的缺陷披露，而不是环境故障。

刷新方式（需 Docker 权限，且要接受重新解析依赖）：

```bash
# 新的 wheel 目录：把待评测提交的 requirements 取并集后离线构建
python3 -m pip wheel --wheel-dir workdir/wheelhouse-next -r <union-requirements.txt>
rm -rf workdir/harbor-images-wheelhouse
python3 harbor/prewarm_wheels.py --prepare --wheels workdir/wheelhouse-next
sudo -n python3 harbor/prewarm_wheels.py --build --tag harbor/review-wheels:next
```

刷新后应先用 `dependency_audit.py --python 3.11` 复核历史提交，确认结论变化，而不是
直接重判旧任务。

## seekdb 自启（无 Docker 时的标准做法）

镜像内的 `pylibseekdb` wheel 带一个可直接运行的 `seekdb` 服务端二进制：

```bash
BIN=$(python3 -c "import pylibseekdb,pathlib;print(pathlib.Path(pylibseekdb.__file__).parent/'seekdb')")
"$BIN" --nodaemon --port 2881 --base-dir /tmp/sdb --data-dir /tmp/sdb/store &
# 等待端口后，用 pymysql 以 root 空密码连接并设置临时密码，写入提交的 .env
```

2026-10-29 实测：得到 `5.7.25-OceanBase seekdb-v1.4.0.0`，`init-db --reset` / `ingest` /
`build-context` 全部通过。因此“沙箱没有 docker”**不是**把 database 标为 blocked 的理由；
只有二进制本身起不来才应标 blocked，并记录端口与凭据位置。

## 内存档位（实测，不是拍脑袋）

同一提交、完整热路径（依赖安装 + 选手自启服务 + 样例回放含重启复用状态）：

| 限制 | 结果 | cgroup `memory.events` |
| ---: | --- | --- |
| 1 GiB | 全部成功，耗时不变 | **`max` 触顶 3804 次**（持续回收 page cache） |
| 2 GiB | 全部成功，耗时不变 | `max`/`oom`/`oom_kill` 均为 0 |
| 4 GiB | 同上（此前默认） | 大量余量 |

实测 `anon` 约 344 MiB，`file`（可回收 page cache）约 1.0 GiB，slab 约 107 MiB。
结论：**1 GiB 能跑但没有余量，不设为默认；所有 profile 默认 2 GiB（含 backend），
重任务可显式 `--memory-mb 4096`。** 本次对照未包含 Pi 模型进程与更大测试集，
所以首次批量仍要采样；`prepare.py --memory-mb` 接受 2048..8192，拒绝 1 GiB 默认值。

`batch.py` 的主机准入预算仍是 light 4 GiB / backend 6 GiB，未因容器下限降低而同步下降：
它包含 verifier、build 与 page cache 余量，故意保留安全边际；要降低并发预算必须先有峰值数据。

## 运行期策略

`harbor/reviewer-skill/runtime_guard.py` 在 agent 启动时写一个 `not_run` 的报告骨架，
并每 5 秒采样 `/sys/fs/cgroup`（内存、swap、pids、CPU）到 **`/tmp/review-runtime-resources.jsonl`**。
指标绝不能写进 `/output/evidence/`：文件在被审阅者哈希后仍会增长，会让 `report_valid` 变成 0。
安装/测试/后端命令通过 `budget <phase> -- CMD` 共享**累计**预算，默认 install 240 秒、
tests/backend 各 120 秒；启动时可改：

```bash
python3 /opt/reviewer-skill/runtime_guard.py start --install-seconds 300
python3 /opt/reviewer-skill/runtime_guard.py limits     # 查看当前生效值
```

这是协作式护栏，不是内核级禁止直接 pip；报告需声明任何绕过。

审阅指令要求：优先使用**选手自己文档里的服务启动方式**；评测侧 18000 服务只是
“提交要求外部服务”时的兜底，访问模式可能和选手客户端假设不同。把 401/422 直接算作
选手缺陷前，必须先确认文档命令连接的是哪个服务。

## 当前范围

`harbor/batch.py`只运行已经固定版本、已生成的Harbor任务，不领取平台任务、不回传成绩。
默认输出计划；只有`--execute`才运行。真实任务必须有本机awaiting_review记录、匹配commit、
剩余安全租约覆盖wall timeout加15分钟人工复核/回传余量。已回传任务禁止重跑。
非oracle模式下，计划阶段还会对提交的显式依赖做只读审计（`harbor/dependency_audit.py`）；
若声明的精确版本未全部命中本地 wheel 集，`--execute` 会拒绝，除非显式 `--allow-uncached`
（冷安装可能超过10分钟，必须是有意的决定）。

- 总并发硬上限4；backend profile硬上限2，暂时为**整条任务占用后端槽**，不是阶段内抢占式调度。
- 同仓库只允许一个batch supervisor，额外taskId flock防重复。
- 每条Harbor运行显式单并发、无自动重试；只用安装好的Harbor0.25.0，不临时uvx下载。
- 每5秒采集主机MemAvailable、磁盘free、PSI、CPU与swap计数，原子更新state.json。
- 资源未知/不足停止准入：默认可用内存12GiB、磁盘150GiB、memory PSI some avg10不高于1%。
- 在基线可用内存之外预留16GiB（12宿主、4控制层/校验）；light按4GiB、backend按6GiB占槽预算，启动前再次核对实时余量。
- 进程超时/收到SIGTERM后向自己的Harbor进程组发送TERM，20秒后KILL；不kill共享Pi。
  如被中断，标记cleanup_required并停止后续任务。Docker容器可能尚未销毁，需要核对本批容器后才能再启动。
- 报告校验目前由Harbor内置管理，**未实现单独2路verifier信号量**；最坏4路校验由4GiB预留覆盖。
- 不支持自动接管崩溃批次或盲目重试；先核对已启动job和容器，不能覆盖已有job目录。

## 环境准备

`harbor/prewarm.py`导出明确commit的PowerContext基础设施源码，复制已有wheel缓存，生成逐文件hash清单。
基础镜像不包含选手minimax目录、.git元数据、平台凭据或旧任务数据库（Git工具本身预装）。PowerContext独立venv，seekdb缓存
用于显式兼容实验，不强行覆盖选手依赖。Node/Pi和APT基础层仍需构建期网络，Python依赖离线安装。

```bash
python3 harbor/prewarm.py --prepare
# 有Docker权限的专用worker；build/health均需显式启用
python3 harbor/prewarm.py --build
python3 harbor/prewarm.py --health
```

准备阶段固定输入hash不等于供应链已全部锁定：基础镜像应提供digest，最终使用本地不可变image ID。
构建超时和健康检查失败必须先解决，不能带病领取新任务；构建宜在评测批次前串行完成。

```bash
# 占位符须替换：LOCAL_IMAGE_ID为不含sha256:前缀的64位ID；batch启动前核对tag实际ID
sudo -n docker tag harbor/prewarm:local harbor/prewarm:sha-LOCAL_IMAGE_ID
python3 harbor/prepare.py --task-id TASK_ID --repo workdir/task-TASK_ID \
  --commit FULL_SHA --base-image sha256:LOCAL_IMAGE_ID --services
```

预热镜像中可信bootstrap自动启动loopback真实PowerContext、检查ready、创建服务端scope，
临时token只留容器600文件；可信Pi wrapper注入服务环境，不把token放CLI参数或日志。
服务是评测基础设施，不算选手交付；安装版本替换须在报告披露。

## 运行

一次领 N 条时必须显式 `--allow-multiple`（默认拒绝在还有未回传任务时再领）：

```bash
set +x; source "$HOME/.config/minimax-ob-judge/platform.env"
./judge/review.sh fetch --minutes 90 --yes                          # 第 1 条
./judge/review.sh fetch --minutes 90 --yes --allow-multiple         # 第 2..N 条
```

每条都要 `prepare.py` 生成独立快照并跑依赖审计；manifest放忽略目录，例：

```json
{"tasks":[
  {"path":"workdir/harbor/review-TASK_ID-SHA12","profile":"backend"}
]}
```

```bash
# 只读资源采样
python3 harbor/resources.py
# 默认计划，不运行，不需要模型Key
python3 harbor/batch.py --manifest workdir/batch.json --batch-id batch-UNIQUE
# 在有Docker权限的worker，专用OB_EVAL_MODEL_KEY已由私密环境注入
(
  set +x
  source "$HOME/.config/minimax-ob-judge/mplan.env"
  python3 harbor/batch.py --manifest workdir/batch.json --batch-id batch-UNIQUE \
    --trials 4 --backends 2 --execute
)
```

本机如需sudo，仅保留专用key，不用sudo -E；不把key作为env命令的key=value参数放入argv。
使用专用worker用户优于root运行；root运行产生的私密产物需在批次完成后只针对该批次修复所有者。
模型主Key在installed agent模式仍可能被选手子进程读取，**短期网关隔离尚未实现**，不能宣称已解决。

进度文件：`runs/harbor-batches/<batch-id>/state.json`，资源序列`resources.jsonl`，原Harbor结果仍在
`runs/harbor/<batch-id>-<taskId>/`。状态finished仅代表Harbor执行完成，不代表通过/得分。

## 后台启动（本机，1~4 路）

```bash
# TRIALS 1..4、BACKENDS 1..2；不给则为单路
TRIALS=4 BACKENDS=2 bash harbor/start_service.sh workdir/batch.json batch-UNIQUE
systemctl --user show harbor-batch-UNIQUE --property=ActiveState,SubState,Result
```

依赖审计未命中缓存时会被拒绝；确认要用冷安装再加 `ALLOW_UNCACHED=1`（会显著变慢）。

启动前只读检查资源与租约，用户systemd服务负责托管；命令几秒返回，不用聊天工具阻塞40分钟。
固定单trial/backend；2400秒是完整评测安全上限，不是需要等待的时间。每次使用唯一batch ID，
旧失败产物不覆盖。不使用LLM子Agent监控，不自动回传。只有明确要求停止才停止服务，不能把
“用户询问耗时”当作取消请求。停止后仍须检查该任务Docker容器是否清理。

`service_entry.py`在进入batch之前清空继承环境，只保留专用模型key和必要运行变量；key由
服务脚本读取仓库外0600配置，不写systemd属性、argv或仓库。当前需sudo使用Docker，服务文件
由root产生，本机检查state.json需使用sudo。运行器并非断点续跑Agent会话：再次启动是同一固定
提交的新trial，必须保留旧运行的证据与中断原因。

## 自动通过闸门（`harbor/triage.py`，无模型）

批量跑完后，用确定性事实判断哪些报告可以自动通过，其余进人工：

```bash
sudo -n python3 harbor/triage.py --batch runs/harbor-batches/batch-UNIQUE --compare-submitted
# 通过候选（需人工授权策略后才可执行；不可逆）
sudo -n python3 harbor/triage.py --batch runs/harbor-batches/batch-UNIQUE \
  --submit-auto-pass --max 20 --yes
```

判定规则：

| 分类 | 条件 |
| --- | --- |
| `auto_pass_candidate` | 六维全 `verified` + 所有证据哈希匹配 + 任务身份与暂存 manifest 一致 + recommendation 为 pass/review + summary 非空 |
| `human` | 任一维 `failed`；或 schema/身份/证据缺失/哈希不符；或存在未 verified 的维度 |

**闸门只自动 pass，永不自动 fail**：`failed` 表示观察到功能失败，但也可能是评测环境造成的误判，必须由人看证据后决定。工具不会把任何 failed/uncertain 试次变成回传。

安全边界：

- `--submit-auto-pass` 还必须给 `--yes` 和正整数 `--max`，逐条串行提交，任一条失败立即停止；
- 提交走既有 `judge/review.py submit`，仍需租约有效、理由非空、平台 ACK 匹配；
- 平台 token 只在控制层加载，绝不进入评测容器；
- 审计记录：每条输出 taskId/commit/六维状态/哈希校验结果/分类理由。

回测（2026-10-29 batch4-run，4 条真实任务，均已有平台ACK的人工结论）：
闸门给出 3 条 auto-pass、1 条 human（正是那条真实 fail），与人工判定 **4/4 一致，0 分歧**。
这只是单批 4 条的一致性，**不等于**对所有提交类型都准确，仍需持续抽样核对。
