# MiniMax M Plan 并发评估

记录日期：2026-10-29。**本页是此前M Plan凭据的历史评估**，不能把一次探针当成平台承诺。
后续用户已更换专用临时高并发key，配置文件仍沿用mplan.env；本文不证明新key的套餐或限额。
当前容量与运行方式以[并发方案](Harbor并发评测方案.md)及[运行器](批量评测运行器.md)为准。
官方说明来源：https://platform.minimax.cn/docs/m-plan/faq （当次查询快照，可能变化）。

## 官方已知限制

MiniMax M Plan 官方 FAQ 说明：

- 有 RPM/TPM 速率限制；超出后通常约一分钟恢复，高峰期可能动态收紧；
- 文本、图像、语音等非视频模型受5小时窗口和周窗口控制；
- M Plan 面向个人交互式使用，官方建议生产环境使用按量付费；
- 官方公开文档没有给出可用于承诺的固定并发槽位。

因此不能根据 Go/Explore/Build 套餐名称推导单Key支持多少个 Harbor trial，也不能把单次成功
当作千人级容量证明。

## 本次探针

时间：2026-10-29；模型：`MiniMax-M3.1-Flash`；国内 Anthropic 兼容端点；每个请求
`max_tokens=8`，只发送短文本，不访问平台任务。

- 并发请求数：2；
- 总墙钟时间：约1.6秒；
- 两个请求均 HTTP 200；
- 一个响应文本精确为 `OK`，另一个响应未精确匹配 `OK`；
- 未收到可据此推断并发上限的429/限流结论；
- 未成功读取额度查询端点，因此没有记录剩余额度或官方账户配额；
- 没有打印或保存Key。

这只能说明这次2路短请求得到HTTP成功，**不能说明稳定支持2路完整审阅，更不能说明支持4/8/100路**。
完整Harbor审阅的token消耗远高于探针，且每条任务还受Docker、seekdb、PowerContext和租约约束。

## 当时的评估建议（非当前调度实现）

1. 用户当时提供QPS=4；它是请求速率信息，不是4个trial的容量证明；
2. 影子评测从 `4 → 2 → 1` 动态降级，若需要扩展再谨慎试更高值；每级跑10–20条短请求和3–5条真实审阅；
3. 记录RPM/TPM、HTTP429/5xx、首Token/总延迟、token、Agent超时、报告完整率和5小时/周额度；
4. 出现限流或p95明显恶化时退回上一级，并做指数退避；
5. Harbor并发必须同时受模型、Docker、后端服务和任务租约限制，不能只看模型返回；
6. 数千份生产评测使用按量付费或专用网关，给每trial短期Key、模型白名单、RPM/TPM/成本限额。

当前YAML默认n_concurrent_trials=4，batch对子Harbor覆盖为1并自行控制总并发。
真实单任务后台试运行固定1路；总上限4/backend上限2来自机器资源预算，不是QPS推导。
