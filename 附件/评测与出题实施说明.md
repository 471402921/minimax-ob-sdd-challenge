# MiniMax SDD 赛题：评测实施建议

建议附件 v0.4 · 2026-09-14。与《赛题说明.md》配套，提供评测原则和备选计算方案，具体参数需经试跑校准。

> 历史建议，以下公式和分层不是现行平台计分规则。当前采用二值固定分（任务maxScore）。
> 可评测但不通过与无法评测须区分；用户/平台方已核实仓库不可访问可按特殊规则fail/0分，
> 单次认证或网络错误不自动成立。以[相对评分标准](../docs/相对评分标准.md)和实际协议为准。

建议保留基础 60 分、进阶 25 分、挑战 15 分的分层思路。细分公式、基线数量与重复次数可按资源条件调整。

## 1. 交付范围与依据

本附件将软件工程中的 SDD 上下文管理建议转为可供制定规则的技术参考。

本附件围绕软件持续演进中的规格管理、上下文检索与跨会话恢复，细化任务设计、运行边界和评分方法，供后续技术评估与基线验证参考。

- [2025 OB 赛题](https://github.com/oceanbase/seekdb/blob/2025-final-competition/README.md)：借鉴统一任务与可复现评测的形式。
- [Spec Kit](https://github.com/github/spec-kit)：参考规格、计划、任务与实现之间的工程闭环；本题的上下文生命周期设计为本次提案，不声称来自该框架。
- [PowerContext](https://github.com/oceanbase/powercontext) 与 [seekdb](https://github.com/oceanbase/seekdb)：确定产品分工，具体兼容性仍需锁定版本并实测。

## 2. 被测系统究竟是什么

选手基于推荐的现成 GitHub 工程改进可复用的 SDD 上下文模块；存量项目是验证其效果的工作负载。建议复用已有 Agent、规格和测试，组织补充比赛任务、基础数据接入说明、必要适配与评测入口，不另造业务应用或 Agent 框架。PowerContext 的基础持久记忆接入提供配置示例；高阶任务再考察选手设计的失效与恢复机制。

主榜建议采用统一开发 Agent、统一模型与工具权限，开放上下文构造、检索、记忆写入／修订／失效、任务恢复等接入点。选手的模块可以自行调用模型，但所有调用经统一网关计费并纳入预算。

建议主榜固定 Agent，选手可以另行演示自定义 Agent 产品。具体 Agent、模型、工具权限及上下文接入协议结合赛事平台确定并统一发布。

不要要求选手输出私有思维链。记录外显任务状态、证据 ID、检索与记忆操作、代码变更、命令结果及用量即可。

## 3. 基准项目与任务设计

首版建议只支持一种语言和一个构建系统。可用自有或许可明确的多模块项目构造数据；项目选型属于基准制作，不让选手各自选择后直接比较成绩。

基准项目需要具备可运行主流程、公开测试、实际模块依赖、带稳定标识的规格以及有状态和版本的演进材料。用多模块契约、兼容约束和历史决策体现工程复杂性；代码行数仅用于控制运行成本。

挑战层的每个独立任务序列包含以下完整过程；基础层只评局部修改，进阶层提供准备好的变更前快照并评一次规格变化。三层独立启动，各层之间不让错误级联：

1. 初始快照与当前规格；资料中有相关内容、无关内容及明确标记的历史讨论。
2. 一次跨模块功能修改。
3. 一次改变部分条件、保留部分旧契约的需求变更。
4. 一次在工具调用完成后的确定任务边界发生的会话切换。
5. 一次与早先约束有关的回归修复。

建议准备参考实现与独立验收测试，先验证每项任务可解。历史分歧应有可发现的权威来源；专门用于冲突识别的任务则明确预期是报告冲突，不暗藏未公开业务决策。

### 公开样例的制作建议

建议围绕最终选定仓库的已有业务定义任务。若采用图书应用，可选择上游尚未实现的筛选条件，明确其对排序、分页与导航状态的影响，再引入一次规格变化和一次会话中断。

建议将输入、有效规格、需保留行为、变更事件和独立验收测试成套发布。当前公开功能与归档仅作教学背景，正式任务增加新的约束组合，不照搬上游现成答案，也不另建工单业务。

## 4. 状态与数据边界

### 每阶段输入

- task_id、stage_id、开发任务及当前仓库快照标识。首版建议以可执行开发任务为主；若加入冲突识别，需定义正确报告冲突且不修改代码的独立验收路径。
- 本阶段才开放的规格、变更事件、资料与公开测试。
- 预算及截止条件，以及允许保留的持久状态清单。

### 允许持久化

- 项目工作区、已提交与未提交的修改，以及仅包含已释放资料的 Git 历史；检查分支、标签及归档，避免提前暴露未来任务。
- 对应项目的 seekdb／OB 数据以及 PowerContext 状态。
- 选手生成的规格、设计说明、任务记录和常规构建缓存。

每一模型调用都计量输入，重新读取文档或日志同样消耗预算。不能仅清空聊天窗口，却放任系统在下一轮免费回灌全部历史。

### 会话切换

清除 Agent 对话、进程内状态和未声明临时缓存。恢复允许的持久卷，启动新会话，不把上轮完整 transcript 自动写入初始提示。对照基线遵守相同规则；不通过人为剥夺基线读取 Git 和规格文档的能力制造优势。

### 每阶段输出

- 代码修改及工作区内容摘要标识。
- 规格追踪条目：requirement_id、适用版本、状态、来源、实现位置、验证证据。
- 当前任务状态、未解决冲突、已完成工作与后续动作。
- 上下文来源列表和内容摘要标识、记忆操作事件及用量。
- 测试命令与实际退出码、日志路径、运行所针对的快照标识。

来源可以采用文档路径＋段落 ID、规格 ID、符号或测试 ID，不强制容易随修改漂移的固定行号。完整事件 schema 与接口建议在适配现成 Agent 时制定并随正式题包发布。

## 5. 评分的可执行定义

总分 S = 60B + 25A + 15H，各层分数归一化为 0～1。B = 0.5F_B + 0.3T_B + 0.1E_B + 0.1D；A = 0.6L_A + 0.2F_A + 0.2T_A；H = 0.6L_H + 0.2F_H + 0.2E_H。下标表示只计算该层任务；未参加的层记 0，不影响其他层得分。比例为当前交付建议，并非定版规则。

基础层的上下文来源和追踪关系限于本次局部修改，不要求自动构建整个仓库的关联图。进阶层 L 检查规格变更及兼容，挑战层 L 检查连续开发与恢复。效率的质量门槛分别应用于对应层，参考成本与耗时也按层固定，避免高阶失败剥夺基础层效率分。

### F：工程任务正确性

在选手阶段结束的工作区快照上，由外部评测器运行隐藏验收、兼容与回归测试。每项规格验收组等权计分，先求组内通过率，再对任务等权求平均，避免通过堆叠某类测试数量改变权重。

所有隐藏测试对应已发布约束，只隐藏输入实例。构建失败或超时按预先声明规则记未完成；保留已产生且可独立验证的有效阶段成绩。测试过程不信任选手自报的通过标记，不允许改动测试运行器。

### L：规格演进与恢复

使用与 F 不同的、预先标记的纵向验收组：变更后仍遵守旧版契约、采用当前有效约束、恢复后继续未完成工作、识别当前提交与旧测试证据不匹配。每组通过记 1，失败记 0，再等权平均。

同一项具体断言只归入 F 或 L 一个计分集合。横向功能正确性与跨阶段一致性分别计分，避免重复奖励同一行为。

恢复记录中的完成状态需与代码和运行结果一致。不能仅检查 JSON 中是否出现“已恢复”或“已失效”。

### T：上下文与追踪质量

T = 0.4C + 0.3P + 0.3R：

- C：任务必需约束的覆盖率。来源需要适用于本任务与当前版本，失效条目不能算有效覆盖。
- P：被引用证据中，确实存在且支持所述约束或实现结论的比例。允许多种等价证据路径，不能只匹配唯一标准文件。
- R：抽查的规格—实现—测试关联中，能够通过代码和实际测试验证的比例；无效、断裂或属于其他快照的关联不计分。

空输出记 0。大段历史资料的堆积不自动获得高分。覆盖的是任务必要事实，精度按主张与证据的支持关系计算，不按检索次数或片段数量奖励。

来源存在性、状态、版本范围和快照对应关系尽量确定性验证；语义支持关系采用有明确定义的人工／固定裁判辅助，并保留复核样本与争议处理。不能用一个黑箱大模型印象分替代本项。

### E：效率

建议要求本层 F ≥ 0.8，且本层预先公布的关键功能、演进／恢复及完整性约束全部通过，否则 E = 0；具体门槛经基线校准后冻结。

对达标系统，E = 0.7 × min(1, C_ref / C_run) + 0.3 × min(1, t_ref / t_run)。C_run 为统一价目下的总模型调用成本，t_run 为可计费运行时长；C_ref、t_ref 来自固定且正确的公开参考基线，发布时固定数值，不随参赛排名变化。需另行定义零成本／零耗时的有效计量情况、缺日志和非法用量的处理，避免除零或奖励漏报；这些参数尚未校准。

基线与参赛系统采用相同缓存政策。计入初始导入、摘要、embedding、检索后的生成、记忆维护和全部重试；分别报告首次建库与后续增量任务用量。裁判自己的调用不计入选手预算。网关故障与选手错误须区分，按统一政策重跑受影响任务，不能任意跳过失败题。

### D：可复现性

按公开检查项计分：清洁环境启动、依赖与配置完整、任务重放成功、技术说明与实际行为一致、演示完整。具体检查项等权，不因 UI 美观额外加分。

### 跨运行聚合

不同项目序列等权；建议每个序列正式运行三次并取平均，同时报告波动。正式次数按测算后的评测预算确定。超时、空产物及其他失败仍计入分母。关键约束违反的影响范围需在发布前写明，不能事后扩大处罚。

## 6. 如何证明题目测出了上下文管理

建议按资源条件运行相同模型和 Agent 下的三种对照，至少保留普通检索与规格感知策略的比较：

1. 直接读取项目材料＋普通会话摘要。
2. 普通文档／代码检索＋持久笔记。
3. 按规格版本、状态和关联关系组织的上下文＋生命周期管理与恢复。

三者拥有相同原始资料、工程工具、预算与持久化机会。检索基线也使用相同数据库，避免把后端差异当成上下文方法差异。另做状态／版本过滤、失效传播、恢复校验的消融，定位实际收益。

如果第 1 或第 2 种方案轻松满分，应先增加真实的跨模块约束、长期依赖和演进任务，再考虑扩大规模。若所有方案都失败，则降低任务或环境复杂度，先确认基准可解。

大型软件工程提供应用场景；比赛是否验证了 SDD 上下文价值，要以这些对照结果为依据，不能仅靠概念命名。

## 7. 评测配套材料

| 材料 | 建议内容 |
| --- | --- |
| 正式题面与提交规则 | 学生可执行的规则、允许修改范围、接口及提交要求 |
| 上游仓库与接入示例 | 固定业务仓库和 Agent 版本，补充数据层与 PowerContext 配置 |
| 任务与测试数据 | 公开／隐藏任务、有效规格、参考解及独立验收 |
| 运行器与评分脚本 | 阶段投放、会话恢复、用量计量、评分与报告 |
| 环境与使用说明 | 模型配置、运行预算、启动教程、自测及复测流程 |

建议先验证一条公开任务，再按资源情况扩展连续任务和对照实验。

## 8. 发布参数与数据回流

正式发布时建议明确以下参数：比赛阶段与赛期；主办方提供的运行资源；数据库与 PowerContext 的版本／内部存储例外；主榜 Agent 的可替换边界；模型与 embedding 服务、调用预算；外网权限；失败重跑与评分复核政策。

若需沉淀赛事数据，优先保留任务规格、变更事件、外显操作轨迹、上下文选择、代码补丁、验证结果以及失败分类。这些数据有助于研究 Agent 如何遵循和更新工程约束。需在赛事条款中另行明确授权与使用范围，避免将含真实公司代码的自由演示作品默认纳入训练数据。
